## Phase Goal

**As a** the X35's owner-navigator (both the developer and the helmsman), **I want to** have the Pi boot headless into a receive-only data backbone that records and decodes the Fastnet bus and the GPS, with replay, simulation and a bus probe, **so that** every later feature can be built and tested before the boat is reachable and the bus can be diagnosed on board in minutes.

## Acceptance Criteria (this plan)
- [ ] GPS position, COG, SOG and UTC from gpsd appear on the diagnostics page with source, age and GPS health
- [ ] The core's clock is GPS-disciplined: unsynced and blocked until valid, with holdover and jump handling; the conventions module is pinned by golden tests
- [ ] The synthetic boat (L2) runs at accelerated speed with faults through the same pipeline, in both UDP and pty-bytes modes

<objective>
Bring GPS and trustworthy time into the backbone, pin the unit and direction conventions, and give developers a synthetic boat with fault injection.

Purpose: the Pi has no RTC and no internet. Every GRIB lookup in Phase 3 depends on the clock, so time must come from GPS and be visibly gated (DATA-04; CONTEXT: Ingest architecture (gpsd), Core clock & state). Conventions bugs (magnetic vs true, FROM vs TOWARDS, kn vs m/s) are silent, so golden tests start on day 1 (CONTEXT: Conventions module). Phase 2 is developed against the L2 synthetic boat (CONTEXT: Replay / simulation L2).

Output: the gpsd JSON client wired into the core (raw-first gps log), the NMEA parser and fake gpsd server for dev and tests, GpsClock with the routing time gate, the units and conventions modules with golden tests, the Fastnet encoder, and `jabuka-sim` with faults.
</objective>
