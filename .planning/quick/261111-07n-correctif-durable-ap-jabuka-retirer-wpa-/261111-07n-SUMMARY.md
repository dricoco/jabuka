# Quick 261111-07n Plan 01: durable fix for the jabuka AP (drop WPA-PSK-SHA256) Summary

A root-owned NetworkManager dispatcher script now runs on every `up` event of jabuka-ap on wlan0. It looks up the AP's wpa_supplicant network id with `list_networks`, so it never assumes id 0. If key_mgmt contains WPA-PSK-SHA256, it resets it to WPA-PSK and runs disconnect then select_network. The wait for wpa_supplicant is bounded, the fix is idempotent, a loop guard stops it after 3 fixes in 60 s, and the script always exits 0. provision.sh installs it, and PI-SETUP.md §4 g and §6 now cover checking it and fixing it by hand.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Loop-guard stamp parsing made robust**
- **Found during:** Task 2
- **Issue:** bash arithmetic on a stamp with a leading zero (`08`) raises an octal error. A stamp in the future, left after chrony steps the clock back, would also stay "younger than 60 s" until reboot and could block the fix.
- **Fix:** the stamp is parsed with `10#`, its length is capped, and only stamps aged 0 to 59 s are kept. Added the test `test_future_and_junk_stamps_do_not_block_the_fix`.
- **Commit:** aa1e52e

**2. [Rule 2 - Robustness] A failed disconnect still attempts select_network**
- **Found during:** Task 2
- **Issue:** the plan allowed either "continue" or "return" after a failed disconnect.
- **Fix:** the script logs `ÉCHEC disconnect ...` and still runs select_network, which on its own restarts the AP with the fixed key_mgmt. The success line is logged only when all three commands return OK.
- **Commit:** aa1e52e
